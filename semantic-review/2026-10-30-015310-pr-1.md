# Whole-account deletion with filesystem-first cleanup

The change adds a password-confirmed owner deletion flow that removes content-addressed bytes before cascading the owner’s SQLite graph, while retaining a credential-free job tombstone and redacted audit evidence. A custom authenticated route derives the owner from the session, requires the exact confirmation phrase and a UUID idempotency key, and verifies the current password through Better Auth. The migration command now constructs a migration-only auth instance with schema validation disabled, while normal production initialization keeps validation enabled. **Watch for:** **confirmed** concurrent replays can turn a completed deletion into a failed tombstone, **confirmed** a lost completion response can strand the browser’s stable key for a replacement owner, and **confirmed** the Chromium suite fails because its memory-delete locator now targets the new account-delete button.

**Verdict**: NEEDS_CHANGES

## High-level view

The lifecycle service separates irreversible file removal from the final database transaction. It inventories artifact and attachment paths under the existing mutation/snapshot lock, validates content-addressed paths and real parent containment, records per-path intent and progress, then redacts audit history and lets the owner cascade remove authentication and owned data in one transaction. Filesystem failures leave the owner and retry job in place.

The HTTP boundary does not accept a user ID. It requires an active session, exact phrase, UUID key, and Better Auth’s sensitive current-password verification before entering the lifecycle service. The Settings form explains that only local ciphertext is removed, recommends export, and redirects only after a completed response.

**Confirmed:** overlapping same-key calls can both observe a pending job before entering the serialized artifact operation. The queued replay then reopens the first request’s completed tombstone after the user is already gone.

**Confirmed:** the stable key’s `localStorage` lifecycle assumes the browser receives the completion response. If deletion commits and that response is lost, a replacement owner in the same browser inherits the old key and receives a permanent conflict from the retained tombstone.

The migration split removes the clean-start Better Auth diagnostic without disabling runtime validation. Focused migration/deletion tests, the full unit/integration suite, lint, typecheck, configured production build, production smoke, persistence smoke, and production dependency audit passed. **Confirmed:** the required Chromium suite fails because the new danger-zone button collides with an existing broad selector, and the implementation report still records the previous schema and test totals.

## Concurrent replay corrupts the completed tombstone

**Confirmed:** `deleteOwnerAccount` reads the job before awaiting `cleanupOwnerArtifactContent`, while the artifact queue serializes only the cleanup body. Two requests using the same valid key can therefore both obtain a non-completed job and enqueue cleanup. The first request removes the user and marks the job completed; the second then unconditionally changes that same job back to `deleting_files`, reaches finalization without a user, and the catch path overwrites the tombstone as `failed` while leaving `completed_at` populated.

```
request A: prepare pending ─┐
                           ├─ serialized cleanup A → user deleted, job completed
request B: prepare pending ─┘
                              serialized cleanup B → job deleting_files
                                                   → owner_missing
                                                   → job failed
```

A direct two-call reproduction produced one fulfilled `completed` result and one `409 owner_missing`; the retained row ended as `state='failed'` with a non-null `completed_at` and the inaccurate error “owner account was retained.” This violates the idempotent replay contract and makes the durable deletion evidence internally contradictory. Re-check job state inside the serialized section, or serialize job preparation and state transition with cleanup, and add a concurrent same-key test that asserts both callers observe completion and that the tombstone remains completed.

Relevant code: `src/modules/lifecycle/account-deletion.ts:172-191`, `src/modules/artifacts/service.ts:326-389`.

## Lost completion response poisons the replacement owner’s browser key

**Confirmed:** the form stores one unscoped key under `nexus-account-deletion-idempotency-key` and removes it only after parsing a completed response. The database intentionally keeps that key globally unique in the tombstone. If the server commits deletion but the response is lost, the deleted owner cannot replay through the route because active authentication is still required; after a replacement owner signs in on the same origin, the form reuses the old key and the server returns `idempotency_conflict` against the old owner hash on every attempt.

The replacement-owner policy is otherwise supported by the single-owner trigger, so the browser key should not permanently bind later owners to an inaccessible completed job. Scope or rotate the local key at the authentication/bootstrap boundary, or return a conflict that the UI can safely recognize and replace without weakening same-owner retry behavior. Cover the commit-with-lost-response followed by replacement-owner flow.

Relevant code: `components/account-deletion-form.tsx:6-35`, `db/migrations/0009_account_deletion.sql:1-18`, `src/modules/lifecycle/account-deletion.ts:85-99`.
