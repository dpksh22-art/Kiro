## OpenAI strict translation remains partial for accepted canonical schemas

**Confirmed, high:** `assertSafeJsonSchema` accepts boolean or schema-valued `additionalProperties` and accepts `allOf`, `anyOf`, and `oneOf` (`src/modules/gateway/schema-validation.ts:78-85`). `openAIStrictWireSchema` preserves an existing `additionalProperties` value and only inserts `false` when the keyword is absent (`src/modules/gateway/provider-schemas.ts:38-43`), while the adapter marks every translated tool and response schema `strict: true` (`src/modules/gateway/adapters/openai-compatible.ts:59-71`). OpenAI's current strict-mode contract requires `additionalProperties: false` on every object. A locally valid schema containing `additionalProperties: true` therefore produces a request-level provider rejection rather than a canonical validation result.

**Confirmed, high:** reverse normalization descends through `properties` and `items`, but returns unchanged when the current schema node has no direct `properties` (`src/modules/gateway/provider-schemas.ts:75-84`). An object selected through an `anyOf` or `oneOf` branch can therefore contain the wire-required `null` for a locally optional child; that null reaches exact canonical validation and is rejected. A review-time reproduction using an object-root schema with a required `payload` whose `anyOf` object branch had an optional child produced `Provider returned structured output that did not match the requested schema.`

Restrict the OpenAI strict input subset before dispatch or translate incompatible object openness without falsely claiming equivalent strict semantics. Reverse normalization must choose and traverse composition branches before canonical validation. Add fixtures for non-false `additionalProperties`, optional children under each supported combinator, and optional objects inside arrays; the new regression covers a direct nested object only.

## Owner abort signals remove outbound deadlines and request cancellation

**Confirmed, high:** every exported GitHub operation now enters `runGitHubOperation`, so `api` always sees an owner signal. Its signal expression uses `AbortSignal.timeout(20_000)` only when neither an owner signal nor an explicit signal exists (`src/modules/github/service.ts:92-102`). Browser repository reads and GitHub writes that do not receive another deadline can therefore remain pending indefinitely, retaining decrypted credentials and an active owner-operation slot until the upstream socket or hosting platform ends them.

**Confirmed, high:** research passes only `ownerOperation.signal` to every connector (`src/modules/research/service.ts:229-231`). `safeFetch` uses its 15-second timeout only when no signal is supplied (`src/modules/research/http.ts:68-71`), so all web, feed, Hacker News, and GitHub research fetches lose that deadline. The route's `request.signal` is not composed until model synthesis (`src/modules/research/service.ts:280-282`), which means a disconnected client cannot stop retrieval; after retrieval, the flow can persist evidence and reserve usage before noticing the cancelled request at provider dispatch.

Compose the owner signal, caller signal, and fixed network timeout for every outbound request rather than selecting one. Add fake-timer or abort-observation tests showing that GitHub requests and research connectors terminate at their fixed deadlines and that request cancellation reaches evidence-only retrieval before persistence or budget reservation.
