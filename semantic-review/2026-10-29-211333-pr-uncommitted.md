# NEXUS AI OS remediation of security and durability boundaries

The remediation closes the conversation/project authorization mismatch, pins validated research DNS answers, recognizes provider stream failures and terminal markers, recovers cancelled leases, enforces per-agent duration, cleans up event polling, requires a production master key, adds CSP, isolates Vitest, and documents a migration-first deployment. Several hard guarantees remain incomplete: owner creation still uses a raceable count check, the SSRF filter admits reserved IPv4 ranges, budget scopes can be bypassed or cannot be configured, crash recovery strands reservations, and GitHub issue retries can still duplicate writes. The production command migrates first, but it starts a standalone build through an unsupported `next start` path.

Watch for: **confirmed blocker** — global and per-task budget scopes do not enforce their stated boundaries; **confirmed blocker** — worker loss leaves reservations charged indefinitely; **confirmed blocker** — GitHub issue recovery can repost a completed operation; **likely blocker** — the owner bootstrap check remains non-atomic; **confirmed high** — reserved IPv4 destinations pass the research allowlist and the documented standalone startup path is unsupported.

**Verdict**: NEEDS_CHANGES

## High-level view

The ownership repair is effective for normal workspace requests: chat now requires the project and existing conversation to belong to the session user, and agent runs validate projects, agents, connections, and models against that user. **Likely concern:** first-account admission still checks the bootstrap token and then separately counts users, so simultaneous authorized signups can both pass before either account is committed.

Research now resolves every redirect target, rejects mapped IPv6, and supplies validated addresses to an Undici dispatcher, closing the original DNS rebinding gap. **Confirmed concern:** the IPv4 predicate remains a hand-written private-range subset and admits non-global ranges such as `192.0.2.0/24`, `198.18.0.0/15`, and `203.0.113.0/24`.

Budget admission now inserts reservations inside SQLite transactions and chat admission rolls conversation, prompt, queued answers, and reservations back together. **Confirmed concerns:** an all-provider policy is nevertheless calculated one provider at a time, an agent “per task” policy is scoped to the whole run, project policies cannot be created through the API, discovered models never receive pricing, and lease recovery has no reservation cleanup path.

Provider adapters now fail on in-band errors and truncated streams, and agent execution has a per-agent abort timer. **Confirmed concern:** the persisted run deadline and max-turn fields remain unused, and timeout failures are recorded as generic execution failures rather than a distinct terminal reason.

Cancelled leases and their attempts are now completed and parent runs are refreshed; event-stream cancellation and request abort both clear polling. **Confirmed concern:** retryable expired attempts are completed with status `ready`, which describes the replacement task state rather than the finished attempt.

GitHub issue creation binds a UUID to a request hash and can reconcile an ambiguous failed POST by searching for a marker. **Confirmed concern:** a pending ledger row causes the next call to POST again before reconciliation, and the browser generates a fresh UUID for each resubmission, so process crashes and user retries can still duplicate issues.

Production configuration now rejects a missing or malformed master key, readiness checks the expected migration, writable storage, and encryption, and responses carry a CSP. Migration-first startup and deployment/backup/restore guidance are present, but **confirmed concern:** `output: "standalone"` is launched with `next start`, which Next.js reports is unsupported.

## Owner bootstrap remains a check-then-create operation

The supplied environment defaults to `NEXUS_ALLOW_SIGNUP=false`, and every signup requires the bootstrap token, so the original open-registration exposure is removed (`.env.example:7-9`, `src/core/auth.ts:46-51`). **Likely blocker:** the hook still performs `SELECT count(*) FROM user` before Better Auth creates the account, without a singleton owner-claim row, unique database invariant, or transaction spanning both operations (`src/core/auth.ts:49-51`). Concurrent requests holding the token can therefore both observe zero users. Replace the count check with a database-serialized one-time claim that is consumed in the same transaction as owner creation, and add a concurrent signup test.

The prior conversation/project mismatch is resolved: chat checks the project by `id` and `user_id`, then checks an existing conversation by `id`, `user_id`, and `project_id` (`src/modules/workspace/chat.ts:38-40`, `48-51`). Agent creation likewise validates the owned project, agents, and model connections (`src/modules/agents/service.ts:53-61`).

## DNS pinning closes rebinding but the address policy is incomplete

`safeFetch` validates the URL, resolves it again, and passes that validated set to an Undici `lookup` callback; redirects recurse through the same admission path (`src/modules/research/http.ts:41-52`, `56-73`). Mapped IPv6, loopback, ULA, and link-local forms are rejected because only `2000::/3` is accepted for IPv6 (`src/modules/research/http.ts:10-19`).

**High, confirmed.** The IPv4 filter only rejects selected private, loopback, link-local, carrier-grade NAT, multicast, and high ranges (`src/modules/research/http.ts:17-19`). A targeted execution showed `assertPublicUrl` accepting `http://192.0.2.1/`, `http://198.18.0.1/`, and `http://203.0.113.1/`. These ranges are not globally routable and may be routed inside test or appliance networks, contrary to the documented non-global-address boundary. Replace the hand-written predicate with canonical CIDR classification that denies every non-global IPv4 and special IPv6 range, then test the complete policy through the pinned connection path.

## Budget reservations are atomic locally but scopes are not faithful

Chat creates the conversation, user message, queued answers, and reservations in one outer transaction (`src/modules/workspace/chat.ts:48-66`). `reserveUsage` also checks settled plus reserved spend and inserts the new reservation in a SQLite transaction (`src/modules/gateway/budgets.ts:17-49`), so concurrent writers against this supported single-writer database cannot all admit against the same prior total.

**Blocker, confirmed.** Every selected policy, including one whose provider is `NULL`, calculates spend with `provider=@provider` (`src/modules/gateway/budgets.ts:20-22`, `35-37`). A focused reproduction created a global 100-micro daily policy, then successfully reserved 60 micros for OpenAI and 60 for Anthropic; the database contained 120 reserved micros. Global policies must aggregate all providers, while provider-specific policies should keep the provider predicate.

The other advertised scopes are also inconsistent. **Blocker, confirmed.** Agent execution passes only `runId`, so a `period='task'` policy uses `run_id=@runId` and combines every task in the run; chat uses one message ID per answer (`src/modules/gateway/budgets.ts:33-37`, `src/modules/agents/runtime.ts:85-90`). The budget API neither accepts nor returns `projectId`, leaving the schema's project-specific policies inaccessible (`app/api/v1/budgets/route.ts:5-6`). Add a task/attempt identity to usage records, define chat task semantics, expose project scope with an ownership check, and test global, provider, project, run, and task combinations.

**Blocker, confirmed.** Provider discovery persists no input price, output price, or currency (`src/modules/gateway/connections.ts:56-61`). Both chat and agents therefore compute `undefined` for every normally discovered model, and any applicable monetary policy fails closed (`src/modules/workspace/chat.ts:31-34`, `src/modules/agents/runtime.ts:85-90`, `src/modules/gateway/budgets.ts:23-25`). The README now documents this behavior, but there is still no path to establish verified pricing, so creating a budget disables all discovered-model execution. Add a versioned, attributable price source or implement another enforceable unit such as tokens or requests.

## Lease recovery strands money and mislabels expired attempts

Cancellation recovery now includes `cancel_requested`, clears its lease, sets the task and running attempt to `cancelled`, and refreshes the parent run (`src/modules/agents/runtime.ts:18-33`). The focused recovery test confirms all three terminal transitions (`tests/integration/recovery.test.ts:6-18`).

**Blocker, confirmed.** A reservation is created before the provider call, but only the live execution catch releases it and only successful completion settles it (`src/modules/agents/runtime.ts:90-112`, `153-175`). `recoverExpired` updates tasks, attempts, and events without finding or releasing the expired attempt's usage reservation (`src/modules/agents/runtime.ts:18-33`). Because usage records carry `run_id` but no task or attempt identity (`db/migrations/0001_core.sql:309-326`), a crashed or cancelled worker can leave a reservation charged forever; a retry creates another reservation and can deny itself against the stale amount. Link reservations to task attempts and settle or release them in the same fenced recovery/completion transactions.

**Follow-up, confirmed.** For an expired retryable task, recovery writes the task's next state, `ready`, into the completed `task_attempts` row (`src/modules/agents/runtime.ts:24-29`). The row has `completed_at`, but its status does not describe the attempt outcome. Use an explicit terminal attempt status such as `lease_expired` or `failed`, while independently putting the task back into `ready`.

## Provider streams fail closed; run-level limits remain declarative

OpenAI-compatible streams reject in-band `error` objects and require `[DONE]`; Anthropic rejects error events and requires `message_stop`; Gemini requires a candidate finish reason (`src/modules/gateway/adapters/openai-compatible.ts:79-97`, `src/modules/gateway/adapters/anthropic.ts:53-76`, `src/modules/gateway/adapters/gemini.ts:62-79`). Chat and agent callers catch those failures, retain partial content where appropriate, and release reservations. The OpenAI regression test covers both an in-band error and truncation (`tests/unit/openai-adapter.test.ts:27-34`).

Per-agent duration is now loaded when claiming work and enforced with an abort timer that is cleared after execution (`src/modules/agents/runtime.ts:42-46`, `93-117`). **High, confirmed.** `task_runs.deadline_at` and `agents.max_turns` remain persisted and exposed but have no runtime reads, and a deadline abort is stored under the generic `execution_failed` code (`db/migrations/0001_core.sql:99-101`, `137-140`, `src/modules/agents/runtime.ts:164-175`). Either enforce these limits and persist a timeout outcome, or remove/de-document fields that are not active controls.

## GitHub issue idempotency still has a crash window

The ledger correctly binds user, repository route, UUID, title, and body hash, rejects key reuse with a different payload, and replays a stored response (`src/modules/github/service.ts:70-80`). If the POST throws after GitHub creates the issue, the catch path searches recent issues for the hidden operation marker (`src/modules/github/service.ts:83-90`).

**Blocker, confirmed.** When a prior ledger row exists with `response_json=NULL`, execution falls through and posts immediately; it only searches for the marker after that new POST throws (`src/modules/github/service.ts:72-89`). A process crash after GitHub accepted the first issue but before line 92 stores its response causes the same-key retry to create a duplicate successfully. The UI also generates `crypto.randomUUID()` inside every submit call (`components/github-console.tsx:10`), so a user retry after an ambiguous response does not reuse the original operation key. Reconcile pending keys before reposting, preserve the key with the pending form operation, and add crash-before-ledger-update and resubmission tests.

## Production safeguards pass, but standalone startup uses the wrong entrypoint

Production parsing now requires a base64 key that decodes to exactly 32 bytes, and readiness verifies the expected migration, a write transaction, and an encrypt/decrypt round trip (`src/core/config.ts:12-20`, `app/api/health/ready/route.ts:4-18`). A targeted missing-key check failed configuration as intended, and the migrated readiness route returned HTTP 200 with schema, storage, and encryption marked available.

The prior missing-CSP gap is resolved: the generated production value includes `default-src 'self'`, `frame-ancestors 'none'`, and `script-src 'self' 'unsafe-inline'` (`next.config.ts:3-24`).

`start:production` runs migrations before start, the image uses a persistent `/app/data` volume under a non-root user, and deployment documentation covers one-writer topology, TLS, backups, restore checks, upgrades, and rollback (`package.json:13-14`, `Dockerfile:13-29`, `compose.yaml:1-24`, `docs/DEPLOYMENT.md`). **High, confirmed.** The build sets `output: "standalone"`, but the production script invokes `next start` (`next.config.ts:5-7`, `package.json:13-14`). A targeted fresh-database launch applied the migration and reached Ready, then emitted: `"next start" does not work with "output: standalone" configuration. Use "node .next/standalone/server.js" instead.` Package the standalone server with its static/public assets and invoke its supported entrypoint after migration.

## Verification passes but misses the remaining hard-boundary cases

The final checks passed ESLint, strict typechecking, 18 Vitest assertions across eight files, three Playwright tests, a configured production build, and `npm audit --omit=dev` with zero advisories. Vitest now includes only unit/integration paths, excludes e2e and generated output, and disables file parallelism for the shared database (`vitest.config.ts:6-15`).

**Follow-up, confirmed.** Tests do not exercise concurrent owner claims, pinned-address dispatch, the allowed reserved ranges, budget reservation races or scope combinations, reservation cleanup after worker death, Anthropic/Gemini failure contracts, actual deadline aborts, GitHub pending-key recovery, production readiness over HTTP, or the container entrypoint. Add these cases before treating the corresponding boundaries as release gates.
