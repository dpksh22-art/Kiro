# IPv6 allowlist closes reported ranges but misses an IETF special allocation

Research URL admission now rejects the reported `64:ff9b:1::/48`, `3fff::/20`, `2001:db8::/32`, mapped-private, private IPv4, loopback, link-local, and metadata cases while admitting ordinary public IPv4 and IPv6 literals. DNS pinning and redirect revalidation remain in place, and all configured unit/integration, build, standalone, browser, and dependency checks pass. The replacement IPv6 policy is still incomplete: it treats most of `2001::/23` as public even though the current IANA registry marks that parent allocation non-globally reachable unless a more-specific allocation permits it. That leaves the same class of SSRF boundary bypass as the prior special-prefix finding.

Watch for: **confirmed high blocker** — `http://[2001:100::1]/` passes admission, but that address is covered only by IANA’s non-globally-reachable `2001::/23` IETF Protocol Assignments entry.

**Verdict**: NEEDS_CHANGES

## High-level view

The requested fix works for the named ranges. Native IPv6 must fall within `2000::/3` and outside an explicit denylist, while mapped-private addresses are canonicalized to IPv4 and rejected by the IPv4 range policy.

**Confirmed high blocker:** the `2000::/3` envelope plus selected exclusions is not equivalent to current IANA global reachability. The registry gives `2001::/23` a non-global default with a small set of globally reachable exceptions, but the implementation blocks selected children and admits the remaining parent space.

**Confirmed coverage gap:** lint, strict TypeScript, 26 unit/integration assertions, the production build, standalone readiness smoke, three Chromium flows, and the production dependency audit passed. The tests include the previously reported ranges but do not exercise an otherwise-unassigned address inside `2001::/23`, so the green gate does not close this release blocker.

## Reported NAT64, documentation, mapped-private, and private ranges are closed

The predicate canonicalizes mapped addresses with `ipaddr.process`. Canonical IPv4 values are admitted only when `ipaddr.js` classifies them as `unicast`; direct probes rejected mapped forms of `127.0.0.1`, `169.254.169.254`, `10.0.0.1`, and `192.168.1.1`. Native IPv6 must match `2000::/3`, which excludes `64:ff9b:1::/48`, loopback, link-local, unique-local, and multicast space, while the explicit denylist includes `2001:db8::/32` and `3fff::/20` (`src/modules/research/http.ts:10-18`).

Every resolved address must pass the predicate, the accepted set is supplied to Undici’s lookup callback, and redirects repeat admission before dispatch. The prior local-use NAT64 examples now fail before a socket can open.

## `2001::/23` still admits non-global destinations

**High blocker, confirmed.** The current IANA IPv6 Special-Purpose Address Registry marks `2001::/23` as not globally reachable unless a more-specific allocation says otherwise. The code does not reject that parent prefix; it rejects selected children including Teredo, benchmarking, deprecated ORCHID, ORCHIDv2, and documentation space, then accepts every other address under the surrounding `2000::/3` envelope (`src/modules/research/http.ts:10-18`). A direct call to `assertPublicUrl("http://[2001:100::1]/")` succeeded even though no more-specific globally reachable registry allocation covers that address.

This is also evidence that the hand-maintained list has drifted from the registry: the current IANA entry marks `2001:20::/28` ORCHIDv2 globally reachable, while the code blocks it. Replace the broad `/3` test plus selected exclusions with a policy generated from or checked against the current IANA global-reachability data. At minimum, apply the non-global `2001::/23` parent default and permit only its current globally reachable exceptions; add a regression for an otherwise-unassigned child such as `2001:100::1`.

The security consequence matches the prior `3fff::/20` finding. A host or private network can route a non-global special-purpose address internally, and the pinned dispatcher will connect to an address once this predicate admits it. The documented claim that research rejects non-public IPv6 therefore remains unenforced for part of IANA’s special-purpose space.

Registry evidence: [IANA IPv6 Special-Purpose Address Registry](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml), checked 2026-10-29. Its `2001::/23` row has Globally Reachable `False [1]`; note 1 says, “Unless allowed by a more specific allocation.”

## Green release checks do not cover the remaining registry default

The checked-in SSRF test rejects `64:ff9b:1::7f00:1`, `3fff::1`, `2001:db8::1`, `::ffff:127.0.0.1`, private and metadata IPv4, documentation and benchmarking IPv4, loopback IPv6, URL credentials, and non-HTTP schemes (`tests/unit/research-security.test.ts:5-9`). It has no case for the non-global default inside `2001::/23`. Its positive case resolves `example.com`, so it also does not isolate literal IPv4 and IPv6 classification.

**Low, confirmed.** Direct release probes admitted `1.1.1.1`, `8.8.8.8`, `2606:4700:4700::1111`, and `2001:4860:4860::8888`. Add these positive literals with the missing non-global-parent regression so correcting the deny policy does not accidentally reject an entire public family.

A configured `npm run check` passed ESLint, strict typechecking, all 26 Vitest assertions across nine files, and the Next.js production build. `npm run test:production` passed the migration-first standalone readiness smoke, `npm run test:e2e` passed owner bootstrap, protected workspace/API, and live constrained-research flows, and `npm audit --omit=dev --audit-level=high` reported zero vulnerabilities. CI invokes migration, tests, build, standalone smoke, and browser checks (`.github/workflows/ci.yml:31-59`), but the absent `2001::/23` case means those checks cannot detect this policy gap.
