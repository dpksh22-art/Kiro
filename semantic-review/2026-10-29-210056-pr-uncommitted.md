# NEXUS AI OS security, durability, and deployment implementation

The uncommitted implementation adds a Next.js AI workspace with local authentication, encrypted provider and GitHub credentials, streaming chat, persistent research, leased agent execution, budgets, and GitHub APIs. Request-to-database paths consistently apply the authenticated user ID, and changed rendering paths escape dynamic text. Several advertised hard boundaries can still be bypassed, disable their feature when enabled, or lose terminal state after a crash. The default test command also fails, and deployment requires undocumented manual preparation.

Watch for: **likely blocker** — research URL validation is separated from the network connection, leaving DNS rebinding and IPv4-mapped IPv6 gaps; **confirmed blockers** — owner registration is open in the supplied environment template and raceable when closed, budget checks neither reserve spend nor support orchestrated runs, provider stream errors become successful messages, cancelled leases can remain stuck after worker loss, configured duration limits are ignored, GitHub issue retries can duplicate external writes, and the documented start/check paths are not release-ready.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed.** Authentication covers the app layout and versioned APIs, and service queries generally scope records by `user_id`. The owner claim is not atomic, `.env.example` keeps sign-up open, and chat can attach a same-user conversation to the wrong project.

**Likely.** Research checks protocols, obvious private ranges, redirects, and response size, but it does not pin approved DNS answers to the connection and misses mapped IPv6 forms.

**Confirmed.** Budget code checks historical usage without reserving capacity. Discovery stores no prices, agents always submit an unknown estimate, and task/project scopes are not applied, making budgets either an availability switch or an overspendable check.

**Confirmed.** Provider adapters ignore in-band error events. A reproduced Anthropic error stream emitted `response.completed`, so partial or empty output can be persisted as success.

**Confirmed.** Cancellation moves active work into a state omitted from lease recovery, and stored duration/turn limits never reach execution. Worker loss can strand a run, while a long-lived provider stream can run indefinitely.

**Confirmed.** GitHub credentials are tenant-scoped and write routes require `confirm: true`, but token permissions are not inspected and issue creation has no idempotency key. An ambiguous retry can duplicate an external write.

**Confirmed.** No exploitable stored or reflected XSS sink was found, but the inline theme script has no Content Security Policy. Production readiness also does not require or validate the credential master key.

**Confirmed.** A configured production build succeeds but logs missing auth tables during collection. `npm start` does not migrate, readiness only checks for `schema_migrations`, deployment/backup instructions are absent, and `npm test` mixes Vitest, Playwright, and generated test copies.

## Owner bootstrap is open by default and not atomic

**Blocker, confirmed.** The supplied deployment template sets `NEXUS_ALLOW_SIGNUP=true` (`.env.example:8`), so an operator following it exposes unrestricted account creation until they manually edit the environment. The server default is closed, but even that policy permits the first account based on a separate `SELECT count(*)` in a pre-auth hook (`src/core/auth.ts:41-45`). Two concurrent first-signup requests can both observe zero users before either insert commits; there is no database singleton constraint around Better Auth's user table. Make the shipped setting closed, provide an explicit one-time bootstrap flow, and serialize the owner claim in the database.

No cross-user object access was found: provider lookup, model selection, project admission, and run reads all include ownership checks (`src/modules/gateway/connections.ts:26-29`, `src/modules/workspace/chat.ts:21-26`, `src/modules/workspace/chat.ts:38-40`, `src/modules/agents/service.ts:115-120`).

**Follow-up, confirmed.** Existing-conversation chat checks `conversation.id` and `user_id` but not `project_id` (`src/modules/workspace/chat.ts:43-49`). A caller can submit project A with their conversation B, after which usage is attributed to project A at `src/modules/workspace/chat.ts:100`. Require the conversation to belong to the supplied project, or derive the project only from the conversation.

## Research network validation can be changed after admission

**Blocker, likely.** `assertPublicUrl` checks one DNS lookup (`src/modules/research/http.ts:20-23`), then `safeFetch` lets the HTTP client resolve the hostname again (`src/modules/research/http.ts:26-31`). An attacker-controlled resolver can return a public address for validation and a private address for connection. The private predicate also misses IPv4-mapped forms such as `::ffff:127.0.0.1` (`src/modules/research/http.ts:6-9`). Pin the validated address while preserving TLS SNI/Host, or enforce destinations through an egress proxy; reject every non-global address after canonicalization. Add rebinding, mapped-IPv6, and redirect tests because current coverage only checks literal IPv4 and schemes (`tests/unit/research-security.test.ts:5-9`).

## Monetary budgets cannot provide the promised hard stop

**Blocker, confirmed.** Model discovery inserts capabilities but never price or currency columns (`src/modules/gateway/connections.ts:56-61`), while chat refuses every model with unknown pricing once any applicable policy exists (`src/modules/gateway/budgets.ts:5-9`, `src/modules/workspace/chat.ts:57-60`). Agent execution is stricter still: it always calls `assertBudget(..., undefined)` (`src/modules/agents/runtime.ts:64-68`), so enabling a provider-wide or all-provider budget makes every agent attempt fail before inference. Populate verified prices or support an explicit token/request ceiling for unknown prices, and pass a defensible reservation amount from every execution path.

**Blocker, confirmed.** Admission sums prior `reserved` and `settled` rows but does not create a reservation (`src/modules/gateway/budgets.ts:17-19`); usage is inserted only after provider completion and immediately marked settled (`src/modules/gateway/budgets.ts:23-33`). Parallel chat requests or workers can all pass against the same old total and spend beyond the hard limit. The `task` period is implemented as all history since 1970 because `assertBudget` has no task/run/message identity (`src/modules/gateway/budgets.ts:5-18`), and project-specific policies in the schema (`db/migrations/0001_core.sql:296-301`) are not selected at all. Reserve admission and update settlement atomically in the same database transaction, scope policy selection by project and task, and release reservations on failure/cancellation.

**Follow-up, confirmed.** Chat persists a new conversation and user message before entering the transaction that can reject the budget (`src/modules/workspace/chat.ts:43-59`). A denied request therefore leaves a completed user turn with no assistant record. Move conversation, prompt, reservation, and queued answers into one admission transaction, or persist an explicit rejected answer state.

## Provider stream errors are persisted as successful answers

**Blocker, confirmed.** The Anthropic adapter parses every SSE payload but only handles `message_start`, `content_block_delta`, and `message_delta`, then unconditionally emits completion (`src/modules/gateway/adapters/anthropic.ts:49-66`). The OpenAI-compatible adapter similarly ignores chunks with an `error` object and emits completion after the loop (`src/modules/gateway/adapters/openai-compatible.ts:81-93`); Gemini also emits completion after any syntactically valid stream (`src/modules/gateway/adapters/gemini.ts:62-74`). A direct reproduction using an Anthropic `event: error` produced only `response.started` followed by `response.completed`. Detect each provider's in-band error and terminal events, reject truncated streams without a valid terminal marker where the protocol provides one, and map the result to `GatewayError` so chat and tasks persist failure rather than success.

The existing adapter test covers a normal delta, usage, and `[DONE]` only (`tests/unit/openai-adapter.test.ts:14-21`). Add contract cases for in-band errors, malformed/truncated termination, abort during body reads, and usage-only final chunks across every adapter.

## Cancellation recovery and execution limits do not bound workers

**Blocker, confirmed.** Cancellation changes leased/running tasks to `cancel_requested` (`src/modules/agents/service.ts:138-146`), but crash recovery scans only `leased` and `running` (`src/modules/agents/runtime.ts:18-28`). If the process exits after the state transition and before the active controller finalizes, no future tick recovers or terminates that task, and the parent run remains `cancel_requested`. Include expired `cancel_requested` leases in recovery and deterministically finalize their attempts, tasks, and run.

**Follow-up, confirmed.** Expired-lease recovery updates only `tasks` and emits an event (`src/modules/agents/runtime.ts:18-28`); it never closes the corresponding `task_attempts` row created at `src/modules/agents/runtime.ts:47-52`. Mark the expired attempt terminal in the same transaction so persisted history does not show workers running forever.

**Blocker, confirmed.** The API accepts and stores `maxDurationSeconds` and `maxTurns` (`app/api/v1/agents/route.ts:15-18`, `src/modules/agents/service.ts:39-43`), but claimed tasks do not carry those fields and execution creates an unbounded `AbortController` (`src/modules/agents/runtime.ts:82-93`). A provider that keeps the stream open can be heartbeated indefinitely, defeating duration and cost bounds. Derive a deadline when creating/claiming a task, abort at that deadline, and persist a distinct timeout terminal state. Either implement turn counting or remove the advertised limit until it exists.

**Follow-up, confirmed.** Cancelling the run-events response sets `closed` without clearing its polling interval (`app/api/v1/runs/[id]/events/route.ts:27-38`). Clear the timer from both stream cancellation and request abort to avoid retaining an interval per disconnected client.

## GitHub confirmation lacks idempotency and least-privilege enforcement

**Blocker, confirmed.** `createIssue` posts immediately after checking a Boolean and has no idempotency lookup (`src/modules/github/service.ts:66-72`), although an `idempotency_keys` table exists (`db/migrations/0001_core.sql:350-359`). If GitHub creates the issue but the client loses the response, retrying the same authorized request creates another issue. Require an idempotency key bound to user, route, repository, and request hash; persist the result before returning and replay it on retries.

**Follow-up, confirmed.** Connecting a token validates only `/user` and stores `{}` as its permissions (`src/modules/github/service.ts:28-35`). Write routes accept caller-supplied `confirm: true` (`app/api/v1/github/issues/route.ts:8-11`, `app/api/v1/github/branches/route.ts:8-11`, `app/api/v1/github/pulls/route.ts:8-11`) without a server-issued approval record bound to the exact repository and payload. Inspect and store token/install permissions, prefer expiring GitHub App installations, optionally restrict repositories, and bind high-impact approvals to a short-lived server-side intent. Continue to enforce GitHub-side branch protections rather than treating the `main`/`master` name check as a protected-branch policy.

## Secret readiness and browser hardening are incomplete

**Follow-up, confirmed.** AES-256-GCM envelopes reject tampering, and credentials are not serialized by connection or GitHub status APIs. However, configuration makes `NEXUS_MASTER_KEY` optional (`src/core/config.ts:6-9`) and validates it only when encrypting or decrypting (`src/core/crypto.ts:6-10`), while readiness checks only for the migration table (`app/api/health/ready/route.ts:2`). Production can report ready while every provider/GitHub credential operation fails. Require a valid master key at production startup, add key identifiers and a rotation procedure, and test readiness against credential-decryption capability without exposing secret material.

**Follow-up, confirmed.** Model output, research bodies, GitHub text, and user input are rendered as React children, for example `components/chat-workspace.tsx:70-72` and `components/run-monitor.tsx:19`, so no changed path interprets this data as HTML. The root does intentionally inject a static inline theme script (`app/layout.tsx:9-10`), while response headers omit Content Security Policy (`next.config.ts:11-20`). Move the theme bootstrap to a nonce/hash-compatible strategy and add a restrictive CSP, including `frame-ancestors`, to reduce the impact of any future rendering sink.

## Startup, readiness, and verification do not form a deployable release path

**Blocker, confirmed.** The runtime start command is only `next start`; migration is a separate manual script (`package.json:11-20`). On a clean configured build, Better Auth repeatedly reported missing `user`, `session`, `account`, `verification`, and `rateLimit` tables during page collection, although the build completed. The migration runner depends on source-side `db/migrations` discovered at runtime (`scripts/migrate.ts:8-21`), but there is no image, entrypoint, persistent-volume layout, backup/restore procedure, or documented order that guarantees migrations run before traffic. Provide a release artifact and entrypoint that runs migrations once, starts as non-root on a persistent single-writer volume, and documents backup/restore and master-key recovery. Make readiness verify the expected migration set and a writable database, not merely return ready for any existing `schema_migrations` table (`app/api/health/ready/route.ts:2`).

**Blocker, confirmed.** `npm test` fails because `vitest.config.ts:6-13` has no include/exclude boundary, so Vitest loads `tests/e2e/workspace.spec.ts:6` as a unit suite and also discovers test copies under `.next/standalone`. The run produced 27 passing unit/integration assertions but one failed Playwright suite load; lint and typecheck passed, all three dedicated Playwright tests passed, the configured production build passed, and `npm audit --omit=dev` reported zero production advisories. Restrict Vitest to unit/integration sources, exclude generated output and e2e specs, then make the clean-environment `npm run check` the release gate.

**Follow-up, confirmed.** Coverage still omits cross-user authorization attempts, concurrent owner bootstrap, DNS rebinding/mapped IPv6, budget reservation races and task periods, provider error streams, worker death during cancellation, deadline enforcement, GitHub retry idempotency, migration-before-start, readiness semantics, and backup/restore. These failure cases should gate the next review.
