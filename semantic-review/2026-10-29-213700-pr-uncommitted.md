# IPv4-only research egress closes the IPv6 SSRF blocker

The research fetcher now rejects native IPv6 literals and DNS answers, removing the incomplete IANA IPv6 allowlist that caused the prior release blocker. Hostnames retain only IPv4 addresses that `ipaddr.js` classifies as unicast, and the fetcher pins that filtered set into Undici before connecting. Focused policy tests, direct probes, a dual-stack live fetch, lint, and typechecking pass. No critical or high blocker remains within the documented single-owner, single-node beta boundary.

Watch for: **confirmed release constraint** — IPv6-only research origins are intentionally unavailable in this beta; this is documented behavior rather than a claimed capability or release blocker.

**Verdict**: APPROVED

## High-level view

The fetcher replaces a fragile native IPv6 special-prefix policy with a fail-closed family boundary. Every native IPv6 address is denied, including globally routable addresses, so newly assigned IANA IPv6 special-purpose ranges cannot bypass application admission.

DNS names remain usable when they have at least one permitted IPv4 answer. The approved IPv4 subset is supplied to the connection-level lookup callback, which preserves hostname-based TLS while preventing a later resolver result from changing the destination.

The release boundary remains the documented personal, single-owner, single-node deployment. Previously verified owner enforcement, budget settlement, task recovery, GitHub issue reconciliation, and production startup findings were used as context; deferred multi-tenant, horizontal-scale, OAuth/webhook, and broader IPv6 capabilities were not treated as current claims.

## Native IPv6 denial replaces the incomplete IANA prefix policy

The address predicate canonicalizes input with `ipaddr.process` and admits only parsed IPv4 values whose range is `unicast` (`src/modules/research/http.ts:10-19`). This closes the prior `2001::/23` blocker without a hand-maintained IPv6 list: `2001:100::1`, public `2606:4700:4700::1111`, local-use NAT64 `64:ff9b:1::7f00:1`, and documentation prefix `3fff::1` all failed direct probes. IPv6-only DNS names fail closed, matching `docs/SECURITY.md` and `docs/ARCHITECTURE.md`.

`ipaddr.process` canonicalizes mapped-private forms to IPv4 before classification, so the suite also rejects `::ffff:127.0.0.1` alongside loopback, metadata, private, benchmarking, and documentation IPv4 destinations (`tests/unit/research-security.test.ts:4-10`).

## Dual-stack domains connect through the filtered IPv4 set

For hostnames, `validatedAddresses` resolves all answers, removes every address rejected by the family and range predicate, and errors when no permitted address remains (`src/modules/research/http.ts:24-33`). `safeFetch` passes only that set to an Undici lookup callback; redirects recurse through the same validation and pinning path (`src/modules/research/http.ts:43-62`). A subsequent system lookup therefore cannot substitute one of the discarded IPv6 answers.

The live release probe resolved `example.com` to two IPv4 and two IPv6 addresses, then fetched `https://example.com/` successfully with HTTP 200 and 577 bytes. Because the pinned set excludes both observed AAAA records, this confirms ordinary dual-stack domain retrieval remains functional through IPv4. A separate probe resolved `ipv6.google.com` only to IPv6 and confirmed admission fails before dispatch.

## Targeted release checks cover the changed boundary

The focused Vitest run passed all 15 SSRF policy cases. ESLint passed for the fetcher and policy test, and strict TypeScript checking passed for the application.

The preceding review recorded passing full static, unit/integration, production build, standalone, browser, and production dependency gates, with native IPv6 classification as its only remaining high blocker. This pass is therefore scoped to that final blocker rather than reopening documented future capabilities.
